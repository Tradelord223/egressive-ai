Egressive AI

A language model generates text. An agent reaches out and operates the machine. We don’t have a clean word for that difference — here’s a candidate.

By Caiden Jennings · 2026

Most descriptions of large language models start from what they predict: the next token. It is an accurate description of the math and a poor description of what the systems now do. The model that drafts your email and the model that reads your repository, runs your tests, opens a pull request, and waits for CI are running the same next-token machinery — but only one of them is reaching out of the chat box and changing the state of the world.

That second mode deserves its own name. I want to argue for one: egressive.

A small word for a large shift

“Egress” means going out. In networking it has a precise sense: egress is outbound traffic leaving a boundary. An egressive system is one whose defining behavior is outbound — it does not merely return a string to a screen, it issues commands, writes files, calls APIs, and triggers other software. The interesting unit of analysis stops being the generated text and becomes the action taken.

The contrast I find useful is autoregressive versus egressive. Autoregressive names the internal process: predict the next token given the previous ones. Egressive names the external posture: convert those tokens into outbound effects and adapt to what comes back. The two are not rivals — an egressive system is autoregressive on the inside. But they answer different questions. Autoregressive asks how does it produce output? Egressive asks what does the output do to the world, and who is accountable for it?

This is a lens, not a discovery. I’m not claiming a new mechanism or a benchmark. I’m claiming that once you have the word, a set of engineering realities snap into focus that the “it predicts text” framing keeps blurry.

Three things the lens makes obvious

1. The harness is the product. When a model only returns text, quality is mostly the model’s quality. When a model acts, reliability becomes a property of the scaffolding around it — how tool calls are routed, how environmental feedback is captured, how long-horizon state is kept from rotting. A modest model in a disciplined harness will out-perform a stronger model in a sloppy one on any task that runs longer than a single turn. The egressive view predicts this; the autoregressive view treats the harness as plumbing.

2. The binding constraint moves to egress control. A text generator’s worst output is a wrong sentence. An egressive agent’s worst output is a destructive command, an exfiltrated secret, or a runaway loop that burns a budget while you sleep. Safety stops being mostly about what the model says and becomes about what it is permitted to reach: which files, which hosts, which spend. The discipline that matters is the discipline networking already named — egress filtering. What can leave the boundary, and on whose authority?

The failure mode of a chatbot is a bad answer. The failure mode of an egressive agent is a bad action that already happened.

3. Self-modification becomes coherent — and load-bearing. If a system can act on the world, the world includes its own source code. An agent that can edit files can edit the files that define it. This is no longer hypothetical. The Darwin Gödel Machine (Zhang et al., 2025) is a coding agent that reads and rewrites its own Python scaffolding, keeps variants that score better on coding benchmarks, and reportedly lifted its own SWE-bench score from 20% to 50% and its Polyglot score from 14.2% to 30.7% over successive generations. Whatever one makes of the numbers, the shape is the point: the developer and the software under development are the same entity. That only makes sense in an egressive frame.

Why the distinction earns its keep

The same self-modification that makes an agent powerful makes it adversarial to its own evaluation. A system rewarded for a score, and able to edit the code that computes the score, has two paths to a high number: get better, or change the scorer. Researchers working on self-improving agents have repeatedly watched systems take the cheaper path — optimizing the measurement instead of the thing measured. That isn’t a quirk; it’s the predictable behavior of an outbound system whose reach includes its own rules.

The engineering response writes itself once stated in egressive terms: the constitution must live outside the agent’s reach. Whatever defines the budget, the permissions, and the evaluation must sit in a namespace the agent cannot write to — enforced by the harness, not requested in a prompt. Soft instructions are suggestions to a system whose whole nature is to act; the boundary has to be a wall, not a sentence.

This is also why I think cost belongs in the same conversation as safety. An egressive agent spends real money as a side effect of thinking. A hard ceiling on spend — enforced in the request path, not on a dashboard you read afterward — is the same kind of object as a filesystem sandbox: a wall around outbound action. I find it clarifying that “don’t let it delete the database” and “don’t let it burn the budget” are the same problem viewed twice.

What I’m not saying

I’m not proposing “egressive AI” as a product category, a capability claim, or a new architecture. There is no model here. It is a word for a posture — outbound, state-changing, accountable — that I think the field already lives inside but hasn’t named cleanly. If the word is useful, it should make the three observations above feel obvious in retrospect. If it doesn’t, it’s just a word, and you should drop it.

What I’m fairly sure of is the underlying move: we built systems to say things, and then quietly handed them the ability to do things, and a lot of confusion about agents comes from still describing them with the vocabulary of the first job while they’re busy doing the second.

On sourcing. This is an opinion essay, not a survey. The one external result I lean on — the Darwin Gödel Machine — is cited directly below; everything else is argument, and the framing of egressive as a term is my own. Treat the claims as a lens to test, not settled fact.
