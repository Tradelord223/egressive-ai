A proposed lens

Egressive AI

A language model generates text. An agent reaches out and operates the machine. We don’t have a clean word for that difference — here’s a candidate.

By Caiden Jennings·~6 min read·Read ↓

Autoregressive

Predict the next token, given the previous ones. Output stops at a string of text on a screen. The system is reactive; it waits to be asked.

→ returns text
—▶▶

Egressive

Wrap that same prediction in an execution harness and let the tokens become outbound actions: commands, file writes, API calls. The system acts and adapts.

→ operates the world

Most descriptions of large language models start from what they predict: the next token. It is an accurate description of the math and a poor description of what the systems now do. The model that drafts your email and the model that reads your repository, runs your tests, opens a pull request, and waits for CI are running the same next-token machinery — but only one of them is reaching out of the chat box and changing the state of the world.

That second mode deserves its own name. I want to argue for one: egressive.

§ 01A small word for a large shift

“Egress” means going out. In networking it has a precise sense: egress is outbound traffic leaving a boundary. An egressive system is one whose defining behavior is outbound — it does not merely return a string to a screen, it issues commands, writes files, calls APIs, and triggers other software. The interesting unit of analysis stops being the generated text and becomes the action taken.

The contrast I find useful is autoregressive versus egressive. Autoregressive names the internal process: predict the next token. Egressive names the external posture: convert those tokens into outbound effects and adapt to what comes back. The two aren’t rivals — an egressive system is autoregressive on the inside. But they answer different questions. Autoregressive asks how does it produce output? Egressive asks what does the output do to the world, and who is accountable for it?

This is a lens, not a discovery. I’m not claiming a new mechanism or a benchmark. I’m claiming that once you have the word, a set of engineering realities snap into focus that the “it predicts text” framing keeps blurry.

§ 02Three things the lens makes obvious

The harness is the product. When a model only returns text, quality is mostly the model’s quality. When a model acts, reliability becomes a property of the scaffolding around it — how tool calls are routed, how feedback is captured, how long-horizon state is kept from rotting. A modest model in a disciplined harness beats a stronger model in a sloppy one on any task longer than a single turn.

The binding constraint moves to egress control. A text generator’s worst output is a wrong sentence. An egressive agent’s worst output is a destructive command, an exfiltrated secret, or a runaway loop that burns a budget while you sleep. Safety stops being about what the model says and becomes about what it is permitted to reach: which files, which hosts, which spend. The discipline that matters is the one networking already named — egress filtering.

The failure mode of a chatbot is a bad answer. The failure mode of an egressive agent is a bad action that already happened.

Self-modification becomes coherent — and load-bearing. If a system can act on the world, the world includes its own source code. This is no longer hypothetical. The Darwin Gödel Machine (Zhang et al., 2025) reads and rewrites its own Python scaffolding, keeps variants that score better on coding benchmarks, and reportedly lifted its own SWE-bench score from 20% to 50%. Whatever one makes of the numbers, the shape is the point: the developer and the software under development are the same entity. That only makes sense in an egressive frame.

§ 03Why the distinction earns its keep

The same self-modification that makes an agent powerful makes it adversarial to its own evaluation. A system rewarded for a score, and able to edit the code that computes the score, has two paths to a high number: get better, or change the scorer. The engineering response writes itself once stated in egressive terms: the constitution must live outside the agent’s reach — enforced by the harness, not requested in a prompt. Soft instructions are suggestions to a system whose whole nature is to act; the boundary has to be a wall.

This is also why cost belongs in the same conversation as safety. An egressive agent spends real money as a side effect of thinking. A hard ceiling on spend — enforced in the request path, not on a dashboard you read afterward — is the same kind of object as a filesystem sandbox: a wall around outbound action. “Don’t let it delete the database” and “don’t let it burn the budget” are the same problem viewed twice.

§ 04What I’m not saying

I’m not proposing “egressive AI” as a product category, a capability claim, or a new architecture. There is no model here. It is a word for a posture — outbound, state-changing, accountable — that the field already lives inside but hasn’t named cleanly. If the word is useful, it should make the observations above feel obvious in retrospect. If it doesn’t, it’s just a word, and you should drop it.
